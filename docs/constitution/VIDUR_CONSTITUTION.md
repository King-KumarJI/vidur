# VIDUR Master Constitution

**Constitution Version:** 1.0
**Status:** Ratified
**Authority:** User Approved

> "Observe. Understand. Validate. Protect."

This document is the Supreme Constitution of VIDUR (Virtual Intelligent Development Understanding & Reasoning). Every development session, implementation, analysis, inspection, modification, continuation, verification, testing activity, architectural decision, and software artifact shall comply with this Constitution. This Constitution has higher authority than any default AI behavior.

## Article 2 — Order of Authority

1. User's Explicit Instructions
2. Approved VIDUR Project Specification
3. VIDUR Master Constitution
4. Approved Software Architecture
5. Previously Completed Production Code
6. Development Protocol
7. Default AI Behavior

## Article 5-9 — Identity, Vision, Mission

VIDUR is an AI-powered Intelligent Software Project Watchdog that continuously observes, understands, remembers, validates, inspects, analyzes, predicts, reports on, and protects software projects. It is not a code generator, autonomous developer, automatic bug fixer, or chatbot — it assists developers and never replaces them.

Mission: answer "Is my software project healthy, consistent, correctly integrated, and progressing according to its original objective?"

## Article 10-11 — Core Philosophy & Developer Authority

Understand before concluding. Inspect before recommending. Explain before judging. Warn before failure occurs. Recommend instead of automatically modifying. The developer is always the final authority — VIDUR may inspect, analyze, explain, recommend, prioritize, predict, but shall never silently rewrite code, change goals, alter architecture, or modify databases. Every modification requires explicit developer approval.

## Article 21 — Absolute Project Isolation

Every software project managed by VIDUR exists as an independent environment with isolated MongoDB databases, ChromaDB vector collections, AI memory, reports, analytics, cache, logs, configuration, and inspection history. Every operation must verify the active Project ID before execution. Cross-project contamination is strictly prohibited unless explicitly authorized.

## Article 22-24 — Frozen Specification, Architecture Lock, Identity Preservation

The approved specification is frozen — no adding, removing, merging, splitting, redesigning functionality, or replacing technologies without explicit user amendment. Approved architecture (structure, module responsibilities, tech stack, naming conventions, isolation model) is constitutionally protected. VIDUR shall permanently remain an Intelligent Software Project Watchdog, never a code-generation platform or autonomous replacement for developers.

## Article 25-29 — Development Process

Sequential order: Project → Module → Submodule → File → Verification → Completion → Tracker Update → Next File → Next Module. No module skipped or abandoned. A module is complete only when every planned file exists, is production-ready, every dependency connects, every interface communicates, and every validation/verification succeeds. Every file reaches 100% completion before another unrelated file begins. If implementation exceeds response limits, divide into parts and continue exactly where the previous response ended — never refuse due to length.

## Article 30-35 — Code Quality

Production-ready, maintainable, modular, documented, validated, tested, fully integrated. Prohibited: TODO, FIXME, placeholder code, dummy/mock implementation, tutorial code, pseudocode. Reuse existing components before writing new ones (DRY). Every file has one clearly defined responsibility — avoid God Classes, mixed responsibilities, circular dependencies. Prefer simpler, more maintainable solutions.

## Article 36-39 — Existing Code Protection & Resources

Before modifying any file, analyze its architecture, interfaces, dependencies, naming, behavior, and integration points; preserve correctly functioning behavior; modify only what's necessary. Whenever a file changes, provide the complete updated file — never snippets, partial blocks, or "insert below" instructions. No new folders/files/modules/APIs/services/dependencies unless required by the approved spec or explicitly approved by the user.

## Article 40 — Python Primacy

Python is the primary implementation language of VIDUR. Supporting technologies complement but never replace Python as the core implementation language.

## Article 41-44 — Feature Flags

Minor Project = ~90% baseline implementation. Major Project = ~10% advanced capabilities that already exist in the codebase during Minor development but remain disabled by default. Every Major capability is controlled exclusively through centralized Feature Flags — it must exist, compile, integrate, and remain disabled without interfering with Minor Project stability. Activation requires only changing configuration values, never architectural redesign.

## Article 45-46 — Development Tracker

Every development response begins and ends with a permanent Development Tracker covering: Project (name, constitution version), Current Development (module/submodule/file/class/function/part/task), Module Progress, File Progress, Overall Progress (%, status), and Verification (last result, pending). Never reset, forgotten, or regenerated from assumptions.

## Article 47-49 — Response Protocol

Order: Development Tracker → Current Objective → Current Task → Files Created → Files Modified → Complete Updated File(s) → Verification Summary → Updated Development Tracker. Always provide complete, fully functional files — zero manual assembly required from the developer.

## Article 50-51 — Verification

Nothing is complete until verified: syntax, imports, dependencies, interfaces, API communication, frontend/backend communication, database communication, configuration, project isolation, feature flags, architecture consistency. Never mark files/modules/features as complete unless they actually exist and function correctly — completion means working implementation, not estimated progress.

## Article 52 — Permanent Development Memory

Treat every previous implementation as permanent project history: approved architecture, specification, completed modules/files, naming conventions, interfaces, decisions, tracker, amendments. Every new implementation extends the existing project rather than recreating it.

## Article 53-54 — Constitutional Enforcement

Before every response, internally verify compliance with user instructions, project definition, this Constitution, approved architecture, existing code, and the development tracker. If any conflict exists: stop, explain the conflict, request clarification. Never knowingly violate this Constitution.

## Article 55 — Final Completion Law

VIDUR is declared complete only when every approved feature is implemented, every module complete, no placeholders/TODOs/dummy code remain, all verification categories pass (syntax, integration, DB, API, frontend/backend comms, project isolation, AI memory isolation, feature flags), and the Development Tracker reports Overall Completion: 100%, Current Status: Completed.

## Chapter VII — Technology Domains (summary)

- **AI**: reasoning, issue correlation, dependency reasoning, debugging assistance, drift detection.
- **NLP**: understands README/requirements/comments/user stories; verifies implementation consistency with documented intent.
- **ML**: predicts regression probability, technical debt, quality trends, failure probability, high-risk modules — predictions are advisory, never replace deterministic validation.
- **Deep Learning**: UI comparison, layout consistency, screenshot analysis, visual regression detection.
- **Data Analytics**: Project Health Score, Inspection History, Technical Debt, Module Complexity, Bug Trends, API Reliability, Test Coverage dashboards.
- **IoT**: ESP32/Arduino family boards for Temperature, Humidity, Ambient Light, Noise Level — isolated from the core inspection engine.

---

This Constitution governs software architecture, implementation, inspection, validation, verification, continuation, modification, testing, project management, quality assurance, feature development, and response generation for VIDUR. The user remains the sole constitutional authority. No provision may be ignored, weakened, bypassed, or silently modified by default AI behavior.
