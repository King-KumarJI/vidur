## Design Notes — API Layer Module

**Starting state of this session (a constitutional conflict, resolved before proceeding).** At session start, `backend/app/api`, `schemas`, `services`, `repositories`, `models`, and `main.py` already existed on disk, fully wired and matching the user's architecture decisions exactly (routes -> services -> repositories/engines; one schema module per route module; Major-tier routes gated behind their feature flag), but as **untracked git files** the Development Tracker had never recorded — the tracker's "Current Development" section still read "API Layer... awaiting next module selection" as if the module had not been started. Per Article 53-54 (stop and resolve conflicts between the tracker and the actual codebase before proceeding), this was investigated first rather than either (a) overwriting the existing implementation or (b) proceeding as if it did not exist. Conclusion: this was leftover work from an earlier, uncommitted session of this same environment (the repository's only commit predates all of modules 4-10), not a divergent or conflicting implementation — Article 52 (Permanent Development Memory) directs treating it as project history to extend, not recreate. This session's own contribution was: full verification of the existing implementation (`py_compile` + `pyflakes` + cross-checking every schema field-for-field against its source engine's `to_dict()`), closing the test-coverage gap (the existing work had only 2 tests, `test_dependencies.py`, versus 43 for Memory and similar counts for every other module), and formally updating this tracker.

**Layering matches the user's explicit decision.** Routes depend only on a per-module `Service` (via `app.api.v1.dependencies`'s one-factory-per-service pattern); no route imports a `core` engine, `app.memory`, or `app.db` directly. Every pipeline service (`InspectionService` through `DeepLearningVisionService`) wraps its `core.*` engine plus `MemoryEngine`, running blocking engine calls off the event loop via `run_in_threadpool` and persisting the resulting report as a side effect (gated on `MINOR_PROJECT_MEMORY`, mirroring how every engine itself is gated on its own flag). `DBHealthService` is the one service backed by a `Repository` rather than an engine, since connectivity health-checking is the API Layer's own capability — no `core.*` module produces a combined Mongo+Chroma status — documented in `models/db_health.py` and `repositories/db_health_repository.py`.

**Cross-module orchestration closes every dependency the underlying engines declared.** `AIReasoningService` runs a fresh `InspectionService.run()` before reasoning (per `AIReasoningEngine.run`'s own requirement for a completed `InspectionReport`). `MLPredictionService` runs inspection (optionally plus reasoning, via `include_reasoning`), fetches `MemoryEngine.health_score_trend()` to feed `QualityTrendPredictor`, then predicts and persists — reusing `InspectionService`/`AIReasoningService` rather than re-deriving their orchestration. `InspectionService` itself feeds `MemoryEngine.history(record_type=INSPECTION, limit=1)`'s stored `snapshot` back into `InspectionEngine.run()` as the drift baseline, closing the loop `InspectionSnapshot`'s own docstring deferred to "the future Memory module" all the way back in the Inspection Engine session.

**Major-tier routes are always present and always compile, per Article 41-44.** `/ml-prediction/run` and `/deep-learning-vision/compare` exist unconditionally; `MLPredictionDisabledError`/`DeepLearningVisionDisabledError` (raised by the underlying engine when its flag is off) are mapped to HTTP 403 by `error_handlers.py`, not hidden by omitting the route. Verified directly in `tests/unit/api/routes/test_ml_prediction.py::test_run_ml_prediction_maps_disabled_feature_flag_to_403` and the equivalent Deep Learning Vision test, against the real, unmodified default-`False` state of both flags.

**One error envelope, registered by base class, per Article 47-49 (uniform response protocol).** `error_handlers.register_exception_handlers` registers a single handler per module against that module's *base* exception class (`InspectionEngineError`, `AIReasoningError`, ..., `ProjectIsolationError`, `DatabaseError`); Starlette resolves a raised exception's handler by MRO walk, so every subclass (`*DisabledError`, `Invalid*Error`) is caught without per-subclass registration. Status code is derived from which of three tuples the exception falls into (`_DISABLED_ERRORS` -> 403, `_INVALID_INPUT_ERRORS`/`_CONTEXT_ERRORS` -> 400, anything else -> 500) — verified exhaustively in `tests/unit/api/test_error_handlers.py` against a throwaway app carrying one route per exception, isolating the mapping logic from any specific route's business logic.

**Schemas mirror engine `to_dict()` output field-for-field, never reinterpreting it (Article 31-32).** Every `*ReportResponse` was cross-checked line-by-line against its source dataclass's `to_dict()` in this session (`inspection_engine`, `ai_reasoning`, `nlp`, `ml_prediction`, `deep_learning_vision`, `memory` models) — no mismatches found. `DeepLearningVisionService._build_snapshot` is the one place a request schema is converted *into* a core dataclass rather than the reverse, since that module is caller-supplied/analysis-only and never captures its own screenshots; covered directly by `tests/unit/services/test_deep_learning_vision_service.py`.

**Test strategy: constructor-injected stubs, not a running server.** Every service test constructs the service with a hand-written stub in place of its engine/sub-service (matching the same DI pattern `MemoryEngine`'s own tests already established with `_FakeRecordStore`/`_FakeSemanticIndex`), so orchestration logic is verified without real file I/O or a live database. Route tests use `fastapi.testclient.TestClient` built **without** entering `app.main`'s lifespan context (no `with TestClient(app) as client:`), so `connect_to_mongo()`/`connect_to_chroma()` never fire and no test pays their real network-timeout cost; `app.dependency_overrides` swaps each route's service for a stub per test, with an autouse fixture (`tests/unit/api/conftest.py`) clearing overrides afterward so tests cannot leak state into each other. Project-scoped routes are each checked once for the `ProjectIsolationMiddleware` 400-on-missing-header behavior, since that behavior is shared, not per-route, logic.

## Design Notes — Specs Backend Module

**Scope was fixed to exactly what the task specified, per Article 38 (no inventing structure beyond what's requested).** The task explicitly named `backend/app/core/specs/` (models, schemas, exceptions, storage) plus `backend/app/api/v1/routes/specs.py`, unlike every prior pipeline module's `core/<engine> + services/<x>_service.py + schemas/<x>_schemas.py` split. No `app/services/specs_service.py` or `app/schemas/specs_schemas.py` was added: Specs has no multi-stage analysis pipeline to justify a separate engine/service layer the way Inspection Engine, AI Reasoning, NLP, ML Prediction, and Deep Learning Vision do — it is ingestion and storage only, so `SpecsStorage` (in `core/specs/storage.py`) owns both persistence and the feature-flag/project-isolation guarantees those other modules split into a dedicated `engine.py`. **Disk I/O and CPU are stateful rates, handled correctly across cycles.** `ComputerMetricsCollector` primes `psutil.cpu_percent(interval=None)` once at construction (its first-call return value is meaningless per psutil's own docs) so every `collect()` call afterward returns a real interval-relative percentage; disk I/O is derived from a stored previous-cycle byte count and timestamp, correctly reporting `None` (missing, not zero) on the very first cycle when no baseline exists yet — verified in `TestComputerMetricsCollector::test_first_cycle_has_no_disk_io_baseline` and `test_second_cycle_computes_disk_io_rate`.

## Design Notes — Specs ML Prediction Engine

**Scope matched exactly what was asked, per Article 38.** `backend/app/core/specs/{session,success_score,predictor}.py` (three new files, one per concern the task named: session derivation, Success Score, and the four-output predictor), route(s) added to the existing `routes/specs.py` (one `GET /specs/prediction` endpoint returning all four outputs together, matching CLAUDE.md's singular "Prediction widget with all four outputs above" - not four separate endpoints, which would be premature fragmentation with no caller). No new `services/`/`schemas/` module was added, extending the precedent the Specs Backend Module already set (ingestion has no multi-stage pipeline to justify one) - the predictor is a `core.*` engine in the same shape as `MLPredictionEngine`, and the route depends on it directly via a `get_specs_prediction_engine` factory, the same one-factory-per-dependency pattern every other route uses.

**Storage/query logic was not duplicated, per the task's explicit instruction.** `SpecsStorage.list_snapshots(project_id, since=None)` is the one new storage method (oldest-first, reusing the existing `_document_to_snapshot` conversion and the same `_require_enabled`/`validate_project_id_format`/`project_scope` guarantees every other `SpecsStorage` method already enforces); `session.py`/`success_score.py`/`predictor.py` never touch MongoDB directly. `since`-filtering happens in Python after retrieval rather than as a Mongo query operator - deliberately, since this collection is small per project and the existing in-memory fake test collection (`tests/unit/core/specs/test_storage.py`) only supports exact-match queries, so this also avoided growing that fake's query language for a single caller.

**Session derivation resolves CLAUDE.md's prose rule to one concrete, documented algorithm** (full reasoning in `session.py`'s module docstring): classify each snapshot ACTIVE / INACTIVE / UNKNOWN from `typing_speed_cpm`/`mouse_activity_rate`; split the full stream into raw runs wherever the gap between consecutive snapshots exceeds `ingestion_interval_minutes + idle_gap_minutes` (default 5 + 10); a raw run is promoted to a session only if it contains at least one ACTIVE snapshot and at least 2 snapshots total; within a qualifying session, each maximal contiguous INACTIVE stretch is one "break" (CLAUDE.md Personal: "break frequency derived from activity gaps"); UNKNOWN snapshots never end a run and are never counted as a break, satisfying CLAUDE.md's explicit "missing personal-activity field means unknown, not no activity - don't let it break the walk." This reading was chosen over a literal "any single non-active snapshot ends the session" reading because that literal reading makes break-frequency-within-a-session structurally impossible to observe, which would make it meaningless as a Success Score input - verified directly in `test_session.py::test_inactive_stretch_within_session_counts_as_one_break` and `test_unknown_snapshot_does_not_end_session_or_count_as_break`.

**Success Score formula (documented in `success_score.py`'s module docstring, mirrored here per the task's explicit request):**

Three independently-optional components, each 0-100, reweighted to sum to 1.0 over whichever are available (never fabricated if none are):

- **A. Duration closeness (weight 0.40).** Requires at least one prior session. `ratio = duration_minutes / mean(historical_sessions.duration_minutes)`; `deviation = clamp(abs(1 - ratio), 0, 1)`; `score_A = 100 * (1 - deviation)`. Peaks at 100 when the session's duration exactly matches the historical average (not "longer is better", per CLAUDE.md).
- **B. Activity consistency (weight 0.35).** For each of typing/mouse whose signal was present on >= 2 snapshots in the session: `cv = clamp(stdev / mean, 0, 1)`; `score_signal = 100 * (1 - cv)`. `score_B` = the mean of whichever signal score(s) are available (both, one, or excluded entirely if neither).
- **C. Break-frequency health (weight 0.25).** Requires a defined `breaks_per_hour` (duration > 0). `score_C = clamp(100 - 40 * abs(breaks_per_hour - 2.0), 0, 100)` - peaks at 100 for 2.0 breaks/hour (one short break roughly every 30 minutes), scores 20 at exactly 0 breaks/hour (low, but explicitly not zero, per CLAUDE.md's "not zero, not excessive"), and 0 at >= 4.5 breaks/hour.

`final_score = sum(weight_i * score_i for available i) / sum(weight_i for available i)`, rounded to 2 decimals. If zero components are available (e.g. a project's very first session with no typing/mouse data at all), the function returns `(None, basis)` rather than a fabricated neutral score - verified in `test_success_score.py::test_no_signal_available_returns_none_not_fabricated`. Every derived session is scored only against the sessions that chronologically preceded it (`predictor.py::_score_sessions` passes `scored[:index]`, never later sessions), so no score is influenced by data that did not yet exist when that session happened.

**Cold start and confidence are never fabricated, per CLAUDE.md's Cold start rule.** Zero derived sessions -> `ConfidenceLevel.NONE` and the upcoming-session `basis` text explicitly says "not a trained-model prediction," falling back to a stated heuristic (last-hour activity signal only: 70/30 split, or 20 if no telemetry at all in the last hour either) - verified in `test_predictor.py::test_predict_cold_start_never_claims_trained_model_confidence`. With history, confidence scales honestly with sample size (`LOW` < 5 sessions, `MEDIUM` < 20, `HIGH` >= 20) since this is always a plain statistical estimate (means over recent sessions, a day-of-week/time-of-day match rate) - never a claim that a separately trained model produced the number, because none exists; `predict()` re-derives sessions and their scores from current `SpecsStorage` history on every call rather than persisting a stale fit.

**Weekly zero-fill is deterministic and independently testable via an injected clock**, matching this codebase's established DI-for-tests precedent (`SpecsStorage.database_provider`, `local_agent.py`'s `clock=time.monotonic`). `SpecsPredictionEngine.__init__` accepts `clock: Optional[Callable[[], datetime]]` (default `utc_now`); `predictor.py::_weekly_coding_time` computes `week_start = now.date() - timedelta(days=now.weekday())` and always emits 7 `WeeklyPoint`s (one per day Monday..Sunday), summing derived sessions' `duration_minutes` by `started_at.date()` and defaulting absent days to `total_minutes: 0.0, session_count: 0` - never omitted or interpolated. Proven against a concrete worked example, not just shape assertions: `test_predictor.py::test_predict_weekly_zero_fill_concrete_worked_example` fixes "now" to Wednesday 2026-01-07, derives one real 20-minute Monday session and one real 30-minute Wednesday session, and asserts all 7 dates/day-names/minutes/session-counts explicitly, including that the other 5 days come back as an explicit `0.0`.

**Both required feature flags enforced, and routes always exist and compile (Article 41-44).** `SpecsPredictionEngine._require_enabled()` checks `MAJOR_PREDICTIVE_DASHBOARDS` (raising the new `SpecsPredictionDisabledError`, registered into `error_handlers.py`'s `_DISABLED_ERRORS` tuple -> HTTP 403); its call into `SpecsStorage.list_snapshots` also enforces the pre-existing `MAJOR_IOT_ENVIRONMENTAL_ANALYTICS` gate (raising `SpecsDisabledError`) - both flags default `False`, and `GET /specs/prediction` exists unconditionally per Article 41-44, verified in `test_specs.py::test_get_prediction_maps_disabled_feature_flag_to_403`.

## Design Notes — Specs Datetime Normalization Fix

**Root cause confirmed exactly as the prior session's design note predicted.** `app.db.mongodb.client`'s `AsyncIOMotorClient` is constructed without `tz_aware=True`, so every BSON date field Motor/PyMongo hands back on read is a naive `datetime` — regardless of the fact that every timestamp this module ever writes (`utc_now()` in `storage.py::ingest`/`add_deadline`) is timezone-aware. `predictor.py`'s `_predict_upcoming_session` (`s.recorded_at >= now - timedelta(hours=1)`, where `now` comes from `self._clock()` = aware `utc_now()`) and `storage.py::get_calendar` (`deadline.due_at >= now`) both compare a Mongo-read value against an aware value, so the very first call against a real, non-empty collection raised `TypeError: can't compare offset-naive and offset-aware datetimes`.

**Fix lives entirely in `storage.py`, at the Mongo read boundary — not in `predictor.py` or `session.py`.** Added `_as_utc_aware(value)` (treats a naive value as UTC, since BSON dates carry no timezone concept at all and every value this module writes was already UTC when stamped; converts an already-aware value to UTC via `.astimezone` for uniformity). Applied at both document-to-dataclass conversion points that read a stored datetime back out of Mongo: `_document_to_snapshot`'s `recorded_at` and `_deadline_from_document`'s `due_at`/`created_at`. This is the *only* place normalization needs to happen — `predictor.py` and `session.py` never touch a raw Mongo document; both only ever consume `SpecsSnapshot`/`SessionRecord`/`Deadline` objects that already passed through `storage.py`'s conversion functions, so once those functions guarantee "always aware," every downstream comparison is safe by construction. Neither file needed code changes; both were re-read in full during this session to confirm that claim rather than assume it (Article 31-32: reuse/verify before writing new code).

**A new test was required because the existing suite could not have caught this, by construction.** Every pre-existing Specs test doubles Mongo with an in-memory fake (`_FakeCollection` in `test_storage.py`, `_FakeStorage` in `test_predictor.py`) that stores and returns the exact Python object it was handed — so every datetime in those tests stayed consistently aware end-to-end and the naive/aware mismatch could never occur, let alone be caught. Added `_NaiveMongoCollection`/`_NaiveMongoDatabase` (`test_storage.py`, duplicated locally in `test_predictor.py` for its own integration test rather than cross-importing) that strips `tzinfo` on write, mimicking real Motor's actual round-trip behavior. Three new `test_storage.py` tests exercise `list_snapshots`, `get_current_snapshot`, and the deadline/calendar path against this fake; one new `test_predictor.py` test (`test_predict_survives_naive_datetimes_returned_by_real_mongo`) routes `SpecsPredictionEngine.predict()` through the *real* `SpecsStorage` (not the usual injected `_FakeStorage`) backed by the same naive-returning fake — the closest a unit test can get to the actual `GET /specs/prediction` request path.

**Fix verified as the actual root cause, not just correlated with the tests passing.** Temporarily reverted `_as_utc_aware`'s two call sites in `_document_to_snapshot`/`_deadline_from_document` and re-ran the 4 new tests: all 4 failed, and the `test_predictor.py` integration test failed with the exact reported error — `TypeError: can't compare offset-naive and offset-aware datetimes` at `predictor.py:180` (`_predict_upcoming_session`'s last-hour-window comparison) — confirming both that the bug is real and that these tests actually detect it rather than passing vacuously. Restored the fix; all tests passed again.

**Manually verified against a real running backend + real MongoDB, not just against unit-test doubles.** Started `uvicorn app.main:app` with `MAJOR_IOT_ENVIRONMENTAL_ANALYTICS=true` and `MAJOR_PREDICTIVE_DASHBOARDS=true` set as process environment variables (not written to the committed `.env` — both flags remain `False` by default per Article 41-44) against the real local MongoDB instance already running on `localhost:27017`. `POST /specs/ingest` (real telemetry), `GET /specs/prediction` (**200**, not 500 — the bug this task was filed against), `POST /specs/deadlines` + `GET /specs/calendar` (**200** — the other fixed comparison path, `due_at >= now`) all succeeded against real Mongo-round-tripped data. The throwaway `verify-datetime-fix` project's MongoDB database was dropped afterward to avoid leaving test data in the real database.

## Design Notes — Specs Current-Snapshot Merge Fix

**Root cause.** `get_current_snapshot` queried Mongo with `find_one(..., sort=[("recorded_at", -1), ("_sequence", -1)])` — i.e. it read only the single most-recently-inserted `specs_snapshots` document and returned it whole. Every ingestion source (the local agent's periodic computer/personal/environmental POST, the frontend's manual sleep-hours/caffeine-intake form POST) calls the same `ingest()` with only the fields it knows about; any field omitted from a given call is stored as `status: "missing"` on *that document* by design (CLAUDE.md's Missing-sensor handling). That per-document contract is correct for `ingest`/storage, but `get_current_snapshot` was treating "the newest document" as "the current state" — so whichever source posted last determined the entire snapshot, and a manual `{sleep_hours}`-only POST arriving after the agent's last 30s cycle silently blanked out every computer/environmental field to missing until the agent's next cycle.

**Fix, in `app/core/specs/storage.py`.** `get_current_snapshot` now fetches the project's full snapshot history (`collection.find({"project_id": ...}).to_list(None)`, same no-query-operator-filtering style `list_snapshots` already uses), sorts newest-first client-side by `(recorded_at, _sequence)` (mirroring the tiebreak `_sequence_counter` exists for), and passes the sorted documents to a new pure helper `_merge_latest_readings`. That helper walks the documents newest-to-oldest maintaining a per-section "pending fields" set; for each document it captures any still-pending field whose stored reading has `status == "present"`, removes it from pending, and stops scanning entirely once every field across all three sections (14 total) is resolved — so a project with a long history does not pay for a full unbounded scan. Any field never present in any document stays explicitly `missing`, satisfying "missing only if never reported" exactly. `recorded_at` on the returned snapshot is the newest document's timestamp (still meaningful as "as of when this merged view is current"), while every individual field value can legitimately trace back to an older document.

**Test added reproduces the exact reported scenario.** `test_get_current_snapshot_merges_fields_across_ingestions_not_just_latest` (`tests/unit/core/specs/test_storage.py`) ingests one full personal+computer+environmental payload, then a second ingestion containing only `{sleep_hours: 8.0}`, then asserts `get_current_snapshot` shows the new `sleep_hours` alongside every computer/environmental/other-personal field from the first ingestion. Confirmed this test fails against the pre-fix code (single-document `find_one` returns only `sleep_hours` present, everything else missing) and passes post-fix. A second new test, `test_get_current_snapshot_field_missing_only_if_never_reported`, guards the other half of the contract — a field truly never ingested must stay `missing`, not be fabricated by the merge.
