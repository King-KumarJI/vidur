## Design Notes — API Layer Module

**Starting state of this session (a constitutional conflict, resolved before proceeding).** At session start, `backend/app/api`, `schemas`, `services`, `repositories`, `models`, and `main.py` already existed on disk, fully wired and matching the user's architecture decisions exactly (routes -> services -> repositories/engines; one schema module per route module; Major-tier routes gated behind their feature flag), but as **untracked git files** the Development Tracker had never recorded — the tracker's "Current Development" section still read "API Layer... awaiting next module selection" as if the module had not been started. Per Article 53-54 (stop and resolve conflicts between the tracker and the actual codebase before proceeding), this was investigated first rather than either (a) overwriting the existing implementation or (b) proceeding as if it did not exist. Conclusion: this was leftover work from an earlier, uncommitted session of this same environment (the repository's only commit predates all of modules 4-10), not a divergent or conflicting implementation — Article 52 (Permanent Development Memory) directs treating it as project history to extend, not recreate. This session's own contribution was: full verification of the existing implementation (`py_compile` + `pyflakes` + cross-checking every schema field-for-field against its source engine's `to_dict()`), closing the test-coverage gap (the existing work had only 2 tests, `test_dependencies.py`, versus 43 for Memory and similar counts for every other module), and formally updating this tracker.

**Layering matches the user's explicit decision.** Routes depend only on a per-module `Service` (via `app.api.v1.dependencies`'s one-factory-per-service pattern); no route imports a `core` engine, `app.memory`, or `app.db` directly. Every pipeline service (`InspectionService` through `DeepLearningVisionService`) wraps its `core.*` engine plus `MemoryEngine`, running blocking engine calls off the event loop via `run_in_threadpool` and persisting the resulting report as a side effect (gated on `MINOR_PROJECT_MEMORY`, mirroring how every engine itself is gated on its own flag). `DBHealthService` is the one service backed by a `Repository` rather than an engine, since connectivity health-checking is the API Layer's own capability — no `core.*` module produces a combined Mongo+Chroma status — documented in `models/db_health.py` and `repositories/db_health_repository.py`.

**Cross-module orchestration closes every dependency the underlying engines declared.** `AIReasoningService` runs a fresh `InspectionService.run()` before reasoning (per `AIReasoningEngine.run`'s own requirement for a completed `InspectionReport`). `MLPredictionService` runs inspection (optionally plus reasoning, via `include_reasoning`), fetches `MemoryEngine.health_score_trend()` to feed `QualityTrendPredictor`, then predicts and persists — reusing `InspectionService`/`AIReasoningService` rather than re-deriving their orchestration. `InspectionService` itself feeds `MemoryEngine.history(record_type=INSPECTION, limit=1)`'s stored `snapshot` back into `InspectionEngine.run()` as the drift baseline, closing the loop `InspectionSnapshot`'s own docstring deferred to "the future Memory module" all the way back in the Inspection Engine session.

**Major-tier routes are always present and always compile, per Article 41-44.** `/ml-prediction/run` and `/deep-learning-vision/compare` exist unconditionally; `MLPredictionDisabledError`/`DeepLearningVisionDisabledError` (raised by the underlying engine when its flag is off) are mapped to HTTP 403 by `error_handlers.py`, not hidden by omitting the route. Verified directly in `tests/unit/api/routes/test_ml_prediction.py::test_run_ml_prediction_maps_disabled_feature_flag_to_403` and the equivalent Deep Learning Vision test, against the real, unmodified default-`False` state of both flags.

**One error envelope, registered by base class, per Article 47-49 (uniform response protocol).** `error_handlers.register_exception_handlers` registers a single handler per module against that module's *base* exception class (`InspectionEngineError`, `AIReasoningError`, ..., `ProjectIsolationError`, `DatabaseError`); Starlette resolves a raised exception's handler by MRO walk, so every subclass (`*DisabledError`, `Invalid*Error`) is caught without per-subclass registration. Status code is derived from which of three tuples the exception falls into (`_DISABLED_ERRORS` -> 403, `_INVALID_INPUT_ERRORS`/`_CONTEXT_ERRORS` -> 400, anything else -> 500) — verified exhaustively in `tests/unit/api/test_error_handlers.py` against a throwaway app carrying one route per exception, isolating the mapping logic from any specific route's business logic.

**Schemas mirror engine `to_dict()` output field-for-field, never reinterpreting it (Article 31-32).** Every `*ReportResponse` was cross-checked line-by-line against its source dataclass's `to_dict()` in this session (`inspection_engine`, `ai_reasoning`, `nlp`, `ml_prediction`, `deep_learning_vision`, `memory` models) — no mismatches found. `DeepLearningVisionService._build_snapshot` is the one place a request schema is converted *into* a core dataclass rather than the reverse, since that module is caller-supplied/analysis-only and never captures its own screenshots; covered directly by `tests/unit/services/test_deep_learning_vision_service.py`.

**Test strategy: constructor-injected stubs, not a running server.** Every service test constructs the service with a hand-written stub in place of its engine/sub-service (matching the same DI pattern `MemoryEngine`'s own tests already established with `_FakeRecordStore`/`_FakeSemanticIndex`), so orchestration logic is verified without real file I/O or a live database. Route tests use `fastapi.testclient.TestClient` built **without** entering `app.main`'s lifespan context (no `with TestClient(app) as client:`), so `connect_to_mongo()`/`connect_to_chroma()` never fire and no test pays their real network-timeout cost; `app.dependency_overrides` swaps each route's service for a stub per test, with an autouse fixture (`tests/unit/api/conftest.py`) clearing overrides afterward so tests cannot leak state into each other. Project-scoped routes are each checked once for the `ProjectIsolationMiddleware` 400-on-missing-header behavior, since that behavior is shared, not per-route, logic.

**Scope matched exactly what was asked, per Article 38.** `backend/app/core/specs/{session,success_score,predictor}.py` (three new files, one per concern the task named: session derivation, Success Score, and the four-output predictor), route(s) added to the existing `routes/specs.py` (one `GET /specs/prediction` endpoint returning all four outputs together, matching CLAUDE.md's singular "Prediction widget with all four outputs above" - not four separate endpoints, which would be premature fragmentation with no caller). **Storage/query logic was not duplicated, per the task's explicit instruction.** `SpecsStorage.list_snapshots(project_id, since=None)` is the one new storage method (oldest-first, reusing the existing `_document_to_snapshot` conversion and the same `_require_enabled`/`validate_project_id_format`/`project_scope` guarantees every other `SpecsStorage` method already enforces); `session.py`/`success_score.py`/`predictor.py` never touch MongoDB directly. `since`-filtering happens in Python after retrieval rather than as a Mongo query operator - deliberately, since this collection is small per project and the existing in-memory fake test collection (`tests/unit/core/specs/test_storage.py`) only supports exact-match queries, so this also avoided growing that fake's query language for a single caller.

**Session derivation resolves CLAUDE.md's prose rule to one concrete, documented algorithm** (full reasoning in `session.py`'s module docstring): classify each snapshot ACTIVE / INACTIVE / UNKNOWN from `typing_speed_cpm`/`mouse_activity_rate`; split the full stream into raw runs wherever the gap between consecutive snapshots exceeds `ingestion_interval_minutes + idle_gap_minutes` (default 5 + 10); a raw run is promoted to a session only if it contains at least one ACTIVE snapshot and at least 2 snapshots total; within a qualifying session, each maximal contiguous INACTIVE stretch is one "break" (CLAUDE.md Personal: "break frequency derived from activity gaps"); UNKNOWN snapshots never end a run and are never counted as a break, satisfying CLAUDE.md's explicit "missing personal-activity field means unknown, not no activity - don't let it break the walk." This reading was chosen over a literal "any single non-active snapshot ends the session" reading because that literal reading makes break-frequency-within-a-session structurally impossible to observe, which would make it meaningless as a Success Score input - verified directly in `test_session.py::test_inactive_stretch_within_session_counts_as_one_break` and `test_unknown_snapshot_does_not_end_session_or_count_as_break`.

**Success Score formula (documented in `success_score.py`'s module docstring, mirrored here per the task's explicit request):**

Three independently-optional components, each 0-100, reweighted to sum to 1.0 over whichever are available (never fabricated if none are):

- **A. Duration closeness (weight 0.40).** Requires at least one prior session. `ratio = duration_minutes / mean(historical_sessions.duration_minutes)`; `deviation = clamp(abs(1 - ratio), 0, 1)`; `score_A = 100 * (1 - deviation)`. Peaks at 100 when the session's duration exactly matches the historical average (not "longer is better", per CLAUDE.md).
- **B. Activity consistency (weight 0.35).** For each of typing/mouse whose signal was present on >= 2 snapshots in the session: `cv = clamp(stdev / mean, 0, 1)`; `score_signal = 100 * (1 - cv)`. `score_B` = the mean of whichever signal score(s) are available (both, one, or excluded entirely if neither).
- **C. Break-frequency health (weight 0.25).** Requires a defined `breaks_per_hour` (duration > 0). `score_C = clamp(100 - 40 * abs(breaks_per_hour - 2.0), 0, 100)` - peaks at 100 for 2.0 breaks/hour (one short break roughly every 30 minutes), scores 20 at exactly 0 breaks/hour (low, but explicitly not zero, per CLAUDE.md's "not zero, not excessive"), and 0 at >= 4.5 breaks/hour.

`final_score = sum(weight_i * score_i for available i) / sum(weight_i for available i)`, rounded to 2 decimals. If zero components are available (e.g. a project's very first session with no typing/mouse data at all), the function returns `(None, basis)` rather than a fabricated neutral score - verified in `test_success_score.py::test_no_signal_available_returns_none_not_fabricated`. Every derived session is scored only against the sessions that chronologically preceded it (`predictor.py::_score_sessions` passes `scored[:index]`, never later sessions), so no score is influenced by data that did not yet exist when that session happened.

**Cold start and confidence are never fabricated, per CLAUDE.md's Cold start rule.** Zero derived sessions -> `ConfidenceLevel.NONE` and the upcoming-session `basis` text explicitly says "not a trained-model prediction," falling back to a stated heuristic (last-hour activity signal only: 70/30 split, or 20 if no telemetry at all in the last hour either) - verified in `test_predictor.py::test_predict_cold_start_never_claims_trained_model_confidence`. With history, confidence scales honestly with sample size (`LOW` < 5 sessions, `MEDIUM` < 20, `HIGH` >= 20) since this is always a plain statistical estimate (means over recent sessions, a day-of-week/time-of-day match rate) - never a claim that a separately trained model produced the number, because none exists; `predict()` re-derives sessions and their scores from current `SpecsStorage` history on every call rather than persisting a stale fit.

**Weekly zero-fill is deterministic and independently testable via an injected clock**, matching this codebase's established DI-for-tests precedent (`SpecsStorage.database_provider`, `local_agent.py`'s `clock=time.monotonic`). `SpecsPredictionEngine.__init__` accepts `clock: Optional[Callable[[], datetime]]` (default `utc_now`); `predictor.py::_weekly_coding_time` computes `week_start = now.date() - timedelta(days=now.weekday())` and always emits 7 `WeeklyPoint`s (one per day Monday..Sunday), summing derived sessions' `duration_minutes` by `started_at.date()` and defaulting absent days to `total_minutes: 0.0, session_count: 0` - never omitted or interpolated. Proven against a concrete worked example, not just shape assertions: `test_predictor.py::test_predict_weekly_zero_fill_concrete_worked_example` fixes "now" to Wednesday 2026-01-07, derives one real 20-minute Monday session and one real 30-minute Wednesday session, and asserts all 7 dates/day-names/minutes/session-counts explicitly, including that the other 5 days come back as an explicit `0.0`.

**Both required feature flags enforced, and routes always exist and compile (Article 41-44).** `SpecsPredictionEngine._require_enabled()` checks `MAJOR_PREDICTIVE_DASHBOARDS` (raising the new `SpecsPredictionDisabledError`, registered into `error_handlers.py`'s `_DISABLED_ERRORS` tuple -> HTTP 403); its call into `SpecsStorage.list_snapshots` also enforces the pre-existing `MAJOR_IOT_ENVIRONMENTAL_ANALYTICS` gate (raising `SpecsDisabledError`) - both flags default `False`, and `GET /specs/prediction` exists unconditionally per Article 41-44, verified in `test_specs.py::test_get_prediction_maps_disabled_feature_flag_to_403`.

## Design Notes — Specs Datetime Normalization Fix

**Root cause confirmed exactly as the prior session's design note predicted.** `app.db.mongodb.client`'s `AsyncIOMotorClient` is constructed without `tz_aware=True`, so every BSON date field Motor/PyMongo hands back on read is a naive `datetime` — regardless of the fact that every timestamp this module ever writes (`utc_now()` in `storage.py::ingest`/`add_deadline`) is timezone-aware. `predictor.py`'s `_predict_upcoming_session` (`s.recorded_at >= now - timedelta(hours=1)`, where `now` comes from `self._clock()` = aware `utc_now()`) and `storage.py::get_calendar` (`deadline.due_at >= now`) both compare a Mongo-read value against an aware value, so the very first call against a real, non-empty collection raised `TypeError: can't compare offset-naive and offset-aware datetimes`.

**Fix lives entirely in `storage.py`, at the Mongo read boundary — not in `predictor.py` or `session.py`.** Added `_as_utc_aware(value)` (treats a naive value as UTC, since BSON dates carry no timezone concept at all and every value this module writes was already UTC when stamped; converts an already-aware value to UTC via `.astimezone` for uniformity). Applied at both document-to-dataclass conversion points that read a stored datetime back out of Mongo: `_document_to_snapshot`'s `recorded_at` and `_deadline_from_document`'s `due_at`/`created_at`. This is the *only* place normalization needs to happen — `predictor.py` and `session.py` never touch a raw Mongo document; both only ever consume `SpecsSnapshot`/`SessionRecord`/`Deadline` objects that already passed through `storage.py`'s conversion functions, so once those functions guarantee "always aware," every downstream comparison is safe by construction. Neither file needed code changes; both were re-read in full during this session to confirm that claim rather than assume it (Article 31-32: reuse/verify before writing new code).

**A new test was required because the existing suite could not have caught this, by construction.** Every pre-existing Specs test doubles Mongo with an in-memory fake (`_FakeCollection` in `test_storage.py`, `_FakeStorage` in `test_predictor.py`) that stores and returns the exact Python object it was handed — so every datetime in those tests stayed consistently aware end-to-end and the naive/aware mismatch could never occur, let alone be caught. Added `_NaiveMongoCollection`/`_NaiveMongoDatabase` (`test_storage.py`, duplicated locally in `test_predictor.py` for its own integration test rather than cross-importing) that strips `tzinfo` on write, mimicking real Motor's actual round-trip behavior. Three new `test_storage.py` tests exercise `list_snapshots`, `get_current_snapshot`, and the deadline/calendar path against this fake; one new `test_predictor.py` test (`test_predict_survives_naive_datetimes_returned_by_real_mongo`) routes `SpecsPredictionEngine.predict()` through the *real* `SpecsStorage` (not the usual injected `_FakeStorage`) backed by the same naive-returning fake — the closest a unit test can get to the actual `GET /specs/prediction` request path.

**Fix verified as the actual root cause, not just correlated with the tests passing.** Temporarily reverted `_as_utc_aware`'s two call sites in `_document_to_snapshot`/`_deadline_from_document` and re-ran the 4 new tests: all 4 failed, and the `test_predictor.py` integration test failed with the exact reported error — `TypeError: can't compare offset-naive and offset-aware datetimes` at `predictor.py:180` (`_predict_upcoming_session`'s last-hour-window comparison) — confirming both that the bug is real and that these tests actually detect it rather than passing vacuously. Restored the fix; all tests passed again.

**Manually verified against a real running backend + real MongoDB, not just against unit-test doubles.** Started `uvicorn app.main:app` with `MAJOR_IOT_ENVIRONMENTAL_ANALYTICS=true` and `MAJOR_PREDICTIVE_DASHBOARDS=true` set as process environment variables (not written to the committed `.env` — both flags remain `False` by default per Article 41-44) against the real local MongoDB instance already running on `localhost:27017`. `POST /specs/ingest` (real telemetry), `GET /specs/prediction` (**200**, not 500 — the bug this task was filed against), `POST /specs/deadlines` + `GET /specs/calendar` (**200** — the other fixed comparison path, `due_at >= now`) all succeeded against real Mongo-round-tripped data. ## Design Notes — Specs Current-Snapshot Merge Fix

**Root cause.** `get_current_snapshot` queried Mongo with `find_one(..., sort=[("recorded_at", -1), ("_sequence", -1)])` — i.e. it read only the single most-recently-inserted `specs_snapshots` document and returned it whole. Every ingestion source (the local agent's periodic computer/personal/environmental POST, the frontend's manual sleep-hours/caffeine-intake form POST) calls the same `ingest()` with only the fields it knows about; any field omitted from a given call is stored as `status: "missing"` on *that document* by design (CLAUDE.md's Missing-sensor handling). That per-document contract is correct for `ingest`/storage, but `get_current_snapshot` was treating "the newest document" as "the current state" — so whichever source posted last determined the entire snapshot, and a manual `{sleep_hours}`-only POST arriving after the agent's last 30s cycle silently blanked out every computer/environmental field to missing until the agent's next cycle.

**Fix, in `app/core/specs/storage.py`.** `get_current_snapshot` now fetches the project's full snapshot history (`collection.find({"project_id": ...}).to_list(None)`, same no-query-operator-filtering style `list_snapshots` already uses), sorts newest-first client-side by `(recorded_at, _sequence)` (mirroring the tiebreak `_sequence_counter` exists for), and passes the sorted documents to a new pure helper `_merge_latest_readings`. That helper walks the documents newest-to-oldest maintaining a per-section "pending fields" set; for each document it captures any still-pending field whose stored reading has `status == "present"`, removes it from pending, and stops scanning entirely once every field across all three sections (14 total) is resolved — so a project with a long history does not pay for a full unbounded scan. Any field never present in any document stays explicitly `missing`, satisfying "missing only if never reported" exactly. `recorded_at` on the returned snapshot is the newest document's timestamp (still meaningful as "as of when this merged view is current"), while every individual field value can legitimately trace back to an older document.

**Test added reproduces the exact reported scenario.** `test_get_current_snapshot_merges_fields_across_ingestions_not_just_latest` (`tests/unit/core/specs/test_storage.py`) ingests one full personal+computer+environmental payload, then a second ingestion containing only `{sleep_hours: 8.0}`, then asserts `get_current_snapshot` shows the new `sleep_hours` alongside every computer/environmental/other-personal field from the first ingestion. Confirmed this test fails against the pre-fix code (single-document `find_one` returns only `sleep_hours` present, everything else missing) and passes post-fix. A second new test, `test_get_current_snapshot_field_missing_only_if_never_reported`, guards the other half of the contract — a field truly never ingested must stay `missing`, not be fabricated by the merge.

## Design Notes — AI Reasoning Ollama Local LLM Upgrade

**Scope decision: the LLM replaces `RecommendationEngine`'s output, not the four upstream analysis stages, per Article 38 and CLAUDE.md's own wording.** CLAUDE.md's AI Reasoning clause reads: "Sends Inspection Engine findings to the local model, parses its response into structured recommendations." `IssueCorrelator`, `DependencyReasoner`, `DebuggingAssistant`, and `DriftReasoner` are deterministic graph/rule analyzers (same-file/same-code grouping, transitive-dependent BFS, a static knowledge-base lookup, a churn-ratio threshold) whose output (`IssueCorrelationGroup`, `DependencyImpactAssessment`, `DebuggingHypothesis`, `DriftInsight`) is also exposed directly through the existing `ReasoningReport`/schemas/routes — replacing them with an LLM would silently change an already-shipped, already-tested API contract with no upstream evidence the task asked for that, and would make VIDUR's own structural findings only as reliable as a model's arithmetic. The genuinely "reasoning" step — turning that structured data into prioritized, human-readable, actionable advice — is exactly what CLAUDE.md's sentence describes and exactly where an LLM adds real value over template strings. `LLMRecommendationEngine.build()` therefore receives all four stages' `to_dict()` output as its prompt and produces the final `Recommendation` list, which is where `RecommendationEngine`'s equivalent rule-based logic already lived.

**Fallback is automatic and structural, not a try/except bolted on at the API layer.** `AIReasoningEngine._execute` (`engine.py`) calls `LLMRecommendationEngine.build()` first; catching `OllamaUnavailableError` or `OllamaResponseParsingError` (both new `AIReasoningError` subclasses) falls back to the pre-existing, untouched `RecommendationEngine.build()` call with the exact same four arguments. Every other stage of `_execute` (correlation, dependency assessment, debugging hypotheses, drift insight) runs identically regardless of which recommendation path is taken — only the final "turn this into recommendations" step differs, so a `ReasoningReport`'s shape is always valid API-contract-wise whether Ollama is up or down.

**`OllamaClient` treats connection failure, timeout, non-2xx status, and unexpected response shape all as one signal: fall back.** `chat_json()` catches `httpx.HTTPError` (whose subclasses cover `ConnectError`, `TimeoutException`, and `HTTPStatusError` uniformly) around the request/status-check, and separately catches `ValueError`/`KeyError`/`TypeError` around extracting `response.json()["message"]["content"]` (Ollama's own documented `/api/chat` response shape) — both paths raise the same `OllamaUnavailableError`, since from the caller's perspective "Ollama sent back garbage" and "Ollama didn't respond at all" warrant the identical rule-based fallback.

**A second, distinct exception (`OllamaResponseParsingError`) exists for a reachable-but-unusable response, to keep the two failure modes independently testable and to enable the CLAUDE.md-required distinction between "Ollama is down" and "Ollama answered but its answer parsed with zero valid recommendations from a non-empty items list."** `LLMRecommendationEngine._parse` treats a genuinely empty `"recommendations": []` (the LLM's own honest "nothing actionable here" answer, which the system prompt explicitly permits) as a valid, non-error result — only a non-empty raw item list where every single item fails per-item validation (missing/invalid `priority`, invalid `category`, or blank `title`/`description`) raises `OllamaResponseParsingError`. Per-item validation is defensive-but-not-silent: malformed individual items are logged and dropped (`_parse_item` returning `None`), so one malformed item never discards otherwise-valid ones alongside it in the same response — verified directly in `test_build_filters_invalid_items_but_keeps_valid_ones`.

**`format: "json"` (Ollama's structured-output mode) plus an explicit example-shaped system prompt, not free-text parsing, is what makes this reliably automatable.** The system prompt asks for exactly `{"recommendations": [{...}]}`; `_parse` also accepts a bare top-level JSON list as a fallback shape (some models/format-json combinations return the array directly rather than wrapped in a key), so a reasonable model deviation doesn't need a second round-trip. `RecommendationPriority`/`InsightCategory` enum values are validated case-insensitively against the exact same enums `RecommendationEngine` already produces, so a `Recommendation` built from the LLM path is byte-structurally indistinguishable from one built from the rule-based path to every existing downstream consumer (schemas, routes, Memory persistence, frontend) — no contract change needed anywhere outside this module.

**`OLLAMA_HOST`/`OLLAMA_MODEL` are the only two new settings, exactly as asked — no new feature flag.** CLAUDE.md's amendment describes Ollama as an always-available, additive enhancement to the always-on `MINOR_AI_REASONING` capability (which already gates the whole module), not a new gated Major-tier capability requiring its own flag; Article 38 (don't invent structure beyond what's requested) argues against adding one. `OLLAMA_MODEL`'s default (`"llama3"`) was set only after confirming via `ollama list` that this machine has `llama3:latest` actually pulled — Ollama resolves an untagged model name to its `:latest` tag, so the plain default matches without needing the tag hardcoded.

**Ollama was genuinely reachable throughout this session (`ollama list` showed `llama3:latest` pulled and `curl localhost:11434/api/tags` responded), which shaped two concrete testing decisions.** First, every `AIReasoningEngine`-constructing test in `test_engine.py` explicitly injects a stub `llm_recommendation_engine` that always raises `OllamaUnavailableError` — without this, this file's tests would have made real, slow, model-dependent HTTP calls on this machine instead of running as fast, deterministic unit tests, which is exactly the CLAUDE.md-required "tests don't require Ollama running" property inverted (they'd have silently required and used it). Second, the one live test (`test_ollama_client.py::test_chat_json_against_live_ollama`, `pytest.mark.skipif`-guarded on a real `GET /api/tags` reachability probe evaluated at collection time) was confirmed to actually fire and pass against the real local model in this session, not merely skip — the full `tests/unit/core/ai_reasoning/` suite took ~12 seconds specifically because of this one real model round-trip, versus sub-second for the other 53 tests, confirming it is genuinely exercising the live path rather than being silently skipped in an environment where it should run.

**Downstream callers outside this module (`app/services/ai_reasoning_service.py`, `tests/unit/core/ml_prediction/test_engine.py`) were deliberately left unmodified.** `AIReasoningService` already constructs `AIReasoningEngine()` with no arguments — this is the correct, intended real-world default (real Ollama with automatic real fallback), needing no change. `ml_prediction`'s test file constructs a real, unstubbed `AIReasoningEngine()` to obtain a real `ReasoningReport` fixture for its own unrelated assertions; because `OllamaClient`'s failure paths are fast (connection-refused returns near-instantly, and this session's environment has Ollama actually reachable so those calls also succeed quickly), this was left as-is rather than expanding this session's touched-file surface into another module's test suite beyond what was asked — noted here rather than silently ignored, per Article 53-54.

## Design Notes — NLP spaCy Linguistic Analyzer Upgrade

**Scope matched exactly what CLAUDE.md's "Real AI/ML/DL/NLP Upgrade" section names for NLP, and exactly what the task asked, per Article 38.** That section reads: "Add spaCy (small pretrained English pipeline, e.g. `en_core_web_sm`) for genuine linguistic analysis of docs/comments, alongside the existing AST-based code parsing and Chroma-embedding semantic comparison -- both stay, spaCy adds real NLP on top." Neither `code_intent_extractor.py` (AST-based) nor `semantic_reasoner.py` (the Major-tier TF-IDF comparator the codebase actually has in this role) was modified at all — both "stay" exactly as they were, byte-for-byte. The only comparison logic touched is `ConsistencyChecker` (the Minor-tier "requirement-to-implementation consistency" component the task explicitly asked to improve), and only additively.

**The improvement is a same-threshold fallback pass, not a replacement of the existing algorithm.** `ConsistencyChecker._requirement_findings`/`_feature_findings` still run the original exact-keyword `tokenize()` overlap check first, unchanged. Only when that check would flag a claim as untraceable does a second pass run: `LinguisticAnalyzer.extract_keywords()` (spaCy lemmas of content-bearing tokens, noun-chunk head lemmas, named-entity words) on both the claim text and the implementation corpus, checked against the *same* `MIN_KEYWORD_OVERLAP_RATIO = 0.5` threshold. A claim is only rescued from being flagged if it has genuine lemma-level overlap with the corpus — this can only reduce false positives (paraphrased/loosely-worded documentation wrongly called untraceable), never suppress a truly-untraceable requirement, since an unrelated corpus has zero overlap under either tokenizer. Verified empirically before writing any test: `"The system should validate incoming requests"` vs. implementation text `"validates incoming request payloads"` scores only 0.25 exact-overlap (a false positive under the old logic alone — `"validate"`≠`"validates"`, `"requests"`≠`"request"`) but 0.75 under spaCy's tagger/parser-informed lemmatizer (`validate`, `incoming`, `request` all normalize to the same lemma on both sides).

**Real pretrained model, not a hand-rolled stemmer — consistent with the upgrade's actual intent.** `LinguisticAnalyzer` uses spaCy's `en_core_web_sm` pipeline (tagger + parser + lemmatizer + NER), not a suffix-stripping stemmer, so lemmatization is POS-context-aware (e.g. `"logs"`/`"log"`, `"validates"`/`"validate"`/`"validating"` all normalize correctly because the tagger resolves each token's part of speech from its sentence context first — this is what "uses sentence structure" means here, not an explicit sentence-splitting step). Noun chunks and named entities are folded into the same flat keyword set (their constituent lemmas are already reachable via plain token iteration in most cases; chunks/entities add robustness for multi-word technical terms and proper nouns that a token-only pass could under-weight).

**Never blocks the pipeline if spaCy or the model isn't installed, matching the same additive-fallback pattern the Ollama-backed AI Reasoning upgrade will need.** `_load_spacy_model()` (module-level, `functools.lru_cache(maxsize=1)`-cached so the ~1-second pipeline load happens at most once per process regardless of how many `ConsistencyChecker`/`LinguisticAnalyzer` instances are constructed) catches both `ImportError` (spaCy not installed) and `OSError` (spaCy installed, model not downloaded), logs a warning with the exact remediation command once, and returns `None`. `LinguisticAnalyzer.extract_keywords()` degrades to the existing `tokenize()` in that case — meaning the linguistic fallback pass becomes a no-op duplicate of the already-computed exact-match ratio (same tokenizer, same result), never a crash and never a behavior regression. Verified directly in `test_extract_keywords_falls_back_to_tokenize_when_model_unavailable`.

**No new feature flag was added, per Article 38 — the task did not name one, and CLAUDE.md's NLP amendment describes spaCy as additive to the always-on Minor-tier consistency check, not a new gated capability.** `ConsistencyChecker`'s constructor grew one new optional parameter (`linguistic_analyzer: Optional[LinguisticAnalyzer] = None`, defaulting to a real instance) — every existing call site (`NLPEngine.__init__`, both direct and via the API service layer) already constructs `ConsistencyChecker()` with no arguments, so nothing broke.

**Dependency installation requires a manual step beyond `pip install`, documented directly in `requirements.txt` and the constitution-required build docs.** spaCy's pretrained pipelines are not PyPI-installable as a normal dependency pin — `python -m spacy download en_core_web_sm` must run once after `pip install -r requirements.txt`. This is called out as a comment immediately below the `spacy==3.7.5` pin in `requirements.txt` rather than left undocumented.

**11 new tests added this session**, all passing against the real installed `spacy`+`en_core_web_sm` (not mocked — this is a genuinely-integrated dependency, matching how `scikit-learn` was verified in the ML Prediction upgrade): 6 in `test_linguistic_analyzer.py` (model availability, blank-text, verb-tense/plural lemmatization against real spaCy output empirically verified via a throwaway script before the test was written, documented-vs-implemented lemma overlap, stopword/short-token filtering, and the forced-unavailable fallback path) and 5 in `test_consistency_checker.py` (one real-spaCy paraphrase-rescue integration test, plus 4 deterministic tests against an injected stub `LinguisticAnalyzer` isolating the checker's OR-fallback boundary logic from spaCy's specific lemmatization choices). ## Design Notes — IoT Firmware Multi-Board Restructuring

**Scope matched Constitution Article 19's requirement exactly, per Article 38.** Article 19 requires support for ESP32 AND Arduino Uno, Nano, Mega, and compatible Arduino-family boards; the prior session's firmware only targeted `esp32dev`, an incomplete gap against the approved spec. This session's task named exactly four PlatformIO environments (`esp32dev`, `uno`, `nanoatmega328new`, `megaatmega2560`) — no additional boards were added speculatively, and the board IDs were verified against real `pio boards atmelavr`/`pio boards` output for the installed platforms rather than assumed, confirming all four names are current and correct (`uno`: Arduino Uno, ATMEGA328P, 2KB RAM; `nanoatmega328new`: Arduino Nano ATmega328 (New Bootloader), 2KB RAM; `megaatmega2560`: Arduino Mega or Mega 2560 ATmega2560, 8KB RAM).

**One shared codebase, not four forked copies.** `firmware/src/main.cpp` is a single file compiled four times (once per PlatformIO environment); the DHT22/BH1750/sound-sensor read logic, the `READ` response builder, and the command-parsing loop are identical text for every board — none of it is duplicated or board-specific. `platformio.ini`'s `[env]` section carries `framework`/`monitor_speed`/`lib_deps` once, applied to all four `[env:*]` sections by PlatformIO's own inheritance behavior, rather than repeating those four lines four times.

**`#ifdef` was used only where hardware genuinely differs, per the task's explicit "only where truly necessary" instruction — verified by asking "does the code path actually differ, or just the wiring?" for each candidate.** Exactly one architecture branch exists (`#if defined(ARDUINO_ARCH_ESP32) ... #else ... #endif`), not four board-specific branches: ESP32's `Wire.begin(sda, scl)` takes software-configurable pin arguments, while every AVR chip's `Wire.begin()` takes none (I2C SDA/SCL are fixed in silicon per chip) — this is a genuine *code* difference. By contrast, the fact that Uno/Nano's I2C physically sits on A4/A5 while Mega's sits on pins 20/21 is a *wiring* fact, not a code difference (the `Wire.begin()` call is byte-for-byte identical on all three AVR boards) — documented in `firmware/README.md`'s per-board wiring tables instead of encoded as a third `#ifdef` branch that would have added complexity without changing what the compiler emits. The same ESP32-vs-AVR split also covers the ADC: ESP32 is a 12-bit ADC on GPIO34, every AVR board is a 10-bit ADC on A0.

**Board identity for `IDENTIFY` comes from an explicit build flag, not a guessed internal macro — a deliberate risk-avoidance decision.** An alternative design would have branched on Arduino-core-internal board macros (`ARDUINO_AVR_UNO`, `ARDUINO_AVR_NANO`, `ARDUINO_AVR_MEGA2560`) to select each board's IDENTIFY string, but this session could not fully confirm in advance whether the "new bootloader" Nano variant (`nanoatmega328new`) defines the same `ARDUINO_AVR_NANO` macro as the classic variant, and getting it wrong would have silently produced an incorrect (or non-compiling) `IDENTIFY` response with no compiler error to catch it. Instead, `VIDUR_BOARD_ID` is passed via `-D` in each environment's `build_flags` in `platformio.ini`, making the environment -> IDENTIFY-string mapping explicit, auditable in one file, and enforced at compile time (`#ifndef VIDUR_BOARD_ID` / `#error` in `main.cpp` if a build somehow omits it).

**The `IDENTIFY` handshake was added as a real, working protocol addition, not just a design proposal — and documented as an explicit version bump, per the task's "not a silent change" instruction.** `docs/specs/serial-protocol.md` gained a new "Board identification handshake (`IDENTIFY`) — protocol v1.1 addition" section (plus updated "Board identification", "Request/response cycle", "Timeouts and failure handling", and "Future work" sections referencing it) rather than editing the existing `READ`-only text in place as if it had always included `IDENTIFY`. The firmware side (`handleIdentifyRequest()` in `main.cpp`) and the agent side (`send_identify_request()` in `local_agent.py`) were both implemented and both exercised by tests (compile-verification for the firmware; 8 new unit tests plus 4 rewritten `collect_environmental_metrics` tests for the agent, see Verification below) — this is a working feature, not a stub.

**`local_agent.py`'s detection logic was changed exactly as instructed: `IDENTIFY` is now the authoritative confirmation step, tried before `READ`, with the existing simulation fallback preserved.** `find_known_serial_port`'s VID:PID pre-filter is unchanged (still narrows which port to even attempt talking to); `collect_environmental_metrics` now calls the new `send_identify_request()` on a matched port and only proceeds to `read_hardware_environmental_line()` if it returns a confirmed board name — an unanswered or malformed `IDENTIFY` response is treated exactly like a failed `READ` was before (fall back to simulation for that cycle, no retry within the cycle, re-scanned fresh next cycle), so the "zero code changes needed when hardware is plugged in" property is preserved end to end.

**Uno/Nano's 2KB RAM budget was treated as a real constraint to engineer against, not a caveat to note and ignore.** The pre-existing single-board `main.cpp` used Arduino's `String` class for both request parsing (`Serial.readStringUntil('\n')`) and JSON response building (`String` concatenation) — acceptable on ESP32's 320KB of RAM, but `String`'s heap allocation and fragmentation risk is a well-known problem on a 2KB AVR chip with no way to observe or bound heap fragmentation at runtime without a debugger. The restructured `main.cpp` replaces both with fixed-size stack buffers: a 16-byte `char[]` command buffer (longest defined command, `IDENTIFY`, is 8 characters) built one byte at a time via `Serial.read()`/`strcmp()`, and a 128-byte `char[]` JSON response buffer built via `dtostrf()` (float -> text) plus `snprintf()` formatting only `%s` substitutions. This also sidesteps a separate, real AVR-specific gotcha: the default Arduino AVR toolchain's `snprintf()`/`sprintf()` do **not** support `%f` unless linked against `libprintf_flt` (not the default), so a naive port of the ESP32 `String`-based formatting to `snprintf("%f", ...)` on AVR would have silently produced garbage or empty output for every floating-point sensor reading — caught by reasoning about the AVR toolchain's known limitations before writing the code, not discovered via a failed test. Real compiled results confirm the engineering worked: Uno and Nano both report **566 of 2048 bytes RAM used (27.6%)** — comfortably within budget, verified directly from `pio run`'s size report, not estimated.

**All three sensor libraries needed zero substitution for AVR support.** `adafruit/DHT sensor library`, `adafruit/Adafruit Unified Sensor`, and `claws/BH1750` all natively support AVR (they predate ESP32 and were originally written for boards like the Uno) — `platformio.ini`'s shared `lib_deps` list is untouched from the ESP32-only version and resolves correctly for all three AVR environments, confirmed by each environment's own `pio run` output showing all three libraries downloaded and linked.
